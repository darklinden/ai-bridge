# A session header is declared by the profile, and its id derived from the conversation's opening

Some upstreams want every request to carry a stable per-conversation id. OpenCode Go is one of them, and it makes the requirement hard rather than advisory: without `x-opencode-session` it answers `400 {"type":"error","error":{"type":"MissingSessionID",…}}` before it even looks at the API key. Measured on 2026-11-11 against `/inference/go/openai/v1/chat/completions` and `/inference/go/anthropic/v1/messages`; the same request with a header added — any `ses_`-prefixed value — succeeds, and both `x-api-key` and `Authorization: Bearer` are accepted on the Anthropic-shaped endpoint. A stateless proxy therefore has to invent something to send, and inventing it badly silently defeats the purpose: the header exists so the upstream can route one conversation consistently and reuse its prompt cache.

**Declared, not inferred.** The header name comes from a profile key, `session_header = "<name>"`, and from nowhere else. Detecting `opencode.ai` in the URL would be the same class of mistake ADR-0002 rejects for wire formats: a hidden vendor branch that no config states and no test can enumerate. When the key is absent, no such header is sent — the proxy does not push one vendor's header at every upstream. The name is validated at load time (`HeaderName`), because the failure it would otherwise cause is a distant upstream 400, not a startup error; names the proxy writes itself or that frame the request (`authorization`, `x-api-key`, `content-type`, `anthropic-version`, `host`, `content-length`, `transfer-encoding`, `connection`) are rejected too, since pointing the key at one of those would replace a value the proxy must control with a conversation id.

**The value is the client's, or else derived.** When the local request already carries the named header with a usable value (non-blank, a legal header value), that value is forwarded as sent: the client is the only party that knows which conversation this is. Otherwise — absent, blank, or unusable — the proxy derives an id from the conversation's opening — the system prompt and the first user message, read from the inbound body *before* conversion and before media preprocessing can rewrite it, so every entry format and every upstream format produce the same id for the same conversation:

- Anthropic Messages: `system` plus the first `messages[]` item with `role: "user"`.
- Chat Completions: the first `system` message plus the first `user` message.
- Responses: `instructions` plus the first user item in `input` (or the plain-string `input`).

The pair is canonicalised (`json_canonical`, so key order cannot move the id) and hashed with FNV-1a into `ses_` + 16 hex. Later turns append messages without touching the opening, so the id persists across a conversation with no table, no TTL and no cleanup — which is the only shape a single-binary, single-upstream, stateless proxy can offer. When neither part exists (a bare probe), the whole body is hashed instead of collapsing every such request onto one shared constant.

**Known degradations, accepted.** Two conversations that open identically share an id — that costs some routing spread and cache locality, never correctness. A client that rewrites its history so the first user turn changes gets a new id mid-conversation, which is indistinguishable from a new conversation from the proxy's point of view. The hash is not cryptographic; a routing id does not need to be.

**Where it sits.** `build_upstream_request` inserts the header after the default auth/content-type headers and before `[headers]`, so an explicit pin in the override table still wins — the same "overrides are last" rule as every other default. The vision target never carries it: a describe call is generated by the proxy, not part of the user's conversation. The value is deliberately absent from the request log; FR-19's line format stays as it is, and a per-request id adds nothing a log reader cannot infer from the conversation itself.

Alternatives rejected: a random per-request value (every turn looks like a new conversation, so the upstream's routing and prompt cache never warm); one fixed value in the profile (works via `[headers]` today, but collapses every conversation into one id — documented as the degraded setup, not the default); forwarding every inbound header so native client session headers pass through (the names are undocumented and client-specific, and it leaks unrelated headers upstream); hashing the whole body (the id would change on every turn).
