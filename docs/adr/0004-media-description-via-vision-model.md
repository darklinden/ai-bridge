# Media handling for text-only upstreams uses a vision model to describe images

When a local request carries images and the upstream is a text-only model, the proxy can replace the image blocks with a text description produced by a separately configured vision model. Everything lives in the profile's `[vision]` table — `upstream_type`, `url`, `api_key`, `model`, plus optional `prompt_mode` / `prompt` / `max_tokens` / `headers` — and the top-level `vision_supplement` key turns the feature on. All images in one request are analyzed together in a single non-streaming vision call; results are cached in-process keyed by an image fingerprint with a TTL. A vision failure degrades to `[Unsupported Image]` and never blocks the request.

`url`, `api_key` and `model` are the capability question: with any of them absent there is nothing to call, so vision is disabled with a WARN and the request proceeds. `upstream_type` is the correctness question: a missing or unknown value is a malformed config and fails startup, exactly like the main upstream's (ADR-0002).

**Off by default is deliberate.** "The upstream is text-only" is decided by a model-name list (`is_confirmed_text_only_model`), which is a heuristic: a newly released vision-capable model the list has not caught up with would have its images silently swapped for descriptions — a loss nobody asked for and nothing reports. Opting in puts that judgement on the user who knows their upstream is text-only (DeepSeek-style), and keeps the default honest for the upstreams that understand images themselves.

This mirrors how Plugin-Deepseek-Vision makes DeepSeek "understand" images via a host vision model, but with our own config surface instead of a plugin host. The sanitizer's original behaviour (replace with a `[Unsupported Image]` placeholder) is kept only as the no-vision-config fallback and the failure path.

**The `[vision]` endpoint must not infer its format from the URL.** A guess based on which markers a path happens to contain fails for a vision URL for exactly the reason it fails for the main upstream: an Anthropic endpoint (`/v1/messages`) carries no marker distinguishing it from a chat path, and misclassifying the vision endpoint is harder to notice than one required line of config (ADR-0002).
