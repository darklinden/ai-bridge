# Outbound body extensions come from the profile, at the outbound seam

A profile may carry a free-form `[extra_body]` table. Its values become JSON and are merged into the body of every request sent to the main upstream — after conversion and after the reasoning policy, at the one place all outbound requests pass through. The table is given to the proxy by the user because the proxy cannot know every vendor's field: a gateway pin is `providerOptions.gateway.only`, some vendors want a `thinking` object, others `safety_settings`, `chat_template_kwargs` or a routing hint. A config key per vendor would grow the schema without bound and would still lag behind whichever provider changed last, so the user — who already declares the upstream and its format — is the authority on the fields it accepts. This is the same reasoning that made the model name a profile value (ADR-0011) and the upstream type explicit (ADR-0002).

**One seam, not one per path.** The body is assembled on every entry × upstream path, pass-through included, and merging in each handler would be the same per-entry duplication DEV-8 already records. The merge therefore lives in `forward::build_upstream_request`, which every path reaches; the handlers stay unaware of the table. The consequence is that the values apply to pass-through too, which is consistent with FR-4's "unconverted, not unmodified": the model override and reasoning policy already reach that path.

**The profile wins, but not over the proxy.** Merging is recursive — objects are completed key by key, scalars and arrays are replaced — and a configured value beats a generated one, because the point is to correct or extend what the proxy produces. What it may not do is take over a value the proxy guarantees: `model` (the profile's model always wins, ADR-0013), `stream` (the client's flag chooses the response pipeline), the conversation container (`messages` / `input`, produced by conversion), and the format's policy fields (`thinking` on Anthropic, `reasoning_effort` on Chat, `reasoning.effort` on Responses, `stream_options.include_usage` on Chat). Those are rejected at startup with the reason text naming where the value really comes from, rather than being silently ignored or silently winning. The set is per format on purpose: a Chat upstream's vendor `thinking` is not the Anthropic master switch, and a Responses upstream may still set `reasoning.summary`.

**Not the vision endpoint.** A `[vision]` call is a generated describe prompt, not a user conversation; a vendor extension aimed at the main model could break it. Leaving the field `None` on that `UpstreamTarget` states the boundary, and a `[vision.extra_body]` could reuse the same slot later if a real need appears.

**Deterministic bytes.** New keys are appended in a fixed key order and existing keys keep their position (`serde_json`'s `preserve_order`), so the same profile always serialises identically — no request-to-request cache churn from the config side.

**No dates, no deletions.** A TOML date/time has no exact JSON value (its serde encoding is a `$__toml_private_datetime` marker object), so it is a startup error telling the user to write a string. Deleting a field the client sent is also out of scope: TOML has no null, and inventing an empty-string sentinel would make a legitimate empty string mean two things. If removal is needed later it gets its own mechanism.

Alternatives rejected: a JSON string blob (`extra_body_json`) — harder to edit and validate than a table, and no more expressive; per-vendor config keys — unbounded schema; model-name-conditional injection — the thing ADR-0011 forbids.
